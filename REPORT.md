## 2. Назначение проекта

**doom_web (IRONHOLLOW)** — браузерный шутер от первого лица в стиле Doom на HTML, CSS и JavaScript. Мир отображается методом raycasting, текстуры и спрайты генерируются кодом. Проект состоит только из статических файлов и не требует серверной части, поэтому его можно разместить в облаке как статический сайт (например, GitHub Pages).

## 4. Использованные элементы Markdown

| Элемент | Где применён |
|---|---|
| Заголовки (`#`, `##`, `###`) | Иерархия разделов README |
| Выделение (`**жирный**`, `*курсив*`) | Ключевые понятия в разделе «О проекте» |
| Маркированные списки | Возможности проекта |
| Нумерованный список | Шаги запуска |
| Таблицы | Архитектура, технологии, управление, автор |
| Ссылки | Репозиторий, локальный адрес, профиль автора |
| Код в строке (`` ` ``) | Имена файлов и клавиши |
| Блоки кода (```` ``` ````) | Команды запуска, дерево каталогов, схема кадра |
| Цитаты (`>`) | Краткое описание и примечание о запуске |

## 5. Архитектурные компоненты

| Компонент | Назначение |
|---|---|
| Конфигурация (`js/config.js`) | Хранит константы и создаёт общий namespace `GAME` |
| Ввод (`js/input.js`) | Принимает команды с клавиатуры, мыши и геймпада |
| Карта и уровни (`js/levels.js`, `js/map.js`) | Описывают ASCII-карты, двери и секретные стены |
| Предметы и игрок (`js/items.js`, `js/player.js`) | Хранят состояние игрока и логику подбора предметов |
| Текстуры и спрайты (`js/textures.js`, `js/sprites.js`) | Процедурно генерируют изображения 64×64 |
| Рендер (`js/renderer.js`) | Строит кадр методом raycasting на `<canvas>` |
| Главный цикл (`js/game.js`) | Выполняет логику с шагом 1/60 с и связывает все модули |

Кадр формируется по цепочке: ввод → обновление логики (игрок, карта, предметы) → рендер → HUD.

## 7. Ответы на контрольные вопросы

**1. Для чего файл README.md используется в GitHub-репозитории?**
Это стартовая страница проекта: GitHub автоматически показывает его при открытии репозитория. В нём описаны назначение проекта, структура, технологии и порядок запуска, поэтому новый участник может разобраться в системе, не читая весь код.

**2. Какие элементы Markdown позволяют структурировать техническую документацию?**
Заголовки задают иерархию разделов, списки перечисляют компоненты и шаги, таблицы сравнивают данные, блоки кода выделяют команды и фрагменты, ссылки ведут к внешним ресурсам, выделение подчёркивает ключевые понятия.

**3. Какие сведения необходимо включить в инструкцию по запуску облачного проекта?**
Требования к окружению (ОС, версии языка и инструментов), порядок получения кода, установку зависимостей, настройку конфигурации без секретов, точные команды запуска в правильной последовательности и способ проверить результат.

**4. Почему реальные пароли, токены и ключи доступа нельзя размещать в README.md и других файлах репозитория?**
Репозиторий может быть публичным, а история Git хранит все версии файлов: попавший в коммит секрет остаётся доступным даже после удаления. Утечка позволяет посторонним получить доступ к облачным ресурсам и данным, поэтому секреты хранят в переменных окружения или специальных хранилищах, а в документации указывают лишь шаблон (например, `.env.example`).

**5. Каким образом качественная документация упрощает командную разработку и сопровождение облачной системы?**
Она ускоряет вход новых участников, фиксирует архитектуру и договорённости, снижает число ошибок при развёртывании и настройке, уменьшает зависимость проекта от одного человека и облегчает поиск причин сбоев.
